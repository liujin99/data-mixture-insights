## 1. Kimi K3 技术报告

**来源**：https://github.com/MoonshotAI/Kimi-K3 (`k3_tech_report.pdf`, 47页)  
**模型规模**：2.8T 总参数 MoE，104B 激活参数，1M context  
**架构亮点**：KDA (Kinematic Dynamic Attention) + Gated MLA 按 3:1 交替，原生多模态

### 1.1 预训练数据（§3.1）

**四大文本领域 + 视觉语料**：
- 文本：Web Text、Code、Mathematics、Knowledge
- 视觉：captions、图文交错、OCR、感知、视频、视觉编程数据（SVG/3D/Webpage/Game/CAD）

**数据清洗流水线**（k3_text.txt:736-739）：
- 三层过滤：规则启发式 + 分类器质量打分 + 去重
- 领域特定采样率由小模型消融实验确定（而非拍脑袋）
- 复述增强（Rephrasing）配方继承自 K2

### 1.2 复述增强（Rephrasing）— 量化结果

继承自 Kimi K2，K2 报告给出了 SimpleQA 上的对照实验：

| 策略 | Epoch | SimpleQA Acc |
|---|---|---|
| 原始 wiki 重复 10 轮 | 10 | 23.76 |
| 复述1次 × 重复10轮 | 10 | 27.39 |
| 复述10次 × 训练1轮 | 1 | **28.94** |

**结论**：多样复述 > 简单重复，每个语料最多复述2次。  
**复述方法**：风格/视角多样 prompt + 分块自回归生成 + 保真度校验。  
**数学语料**：改写为"学习笔记"风格（SwallowMath 方法）+ 跨语言翻译。

### 1.3 训练配方（§3.3）

**渐进式上下文扩展（四阶段课程）**（k3_text.txt:822-826）：
- 预训练阶段：8K → 64K
- cooldown 阶段：256K → 1M
- 长序列计算集中在小部分训练预算内

**长上下文数据处理**（k3_text.txt:812-820）：
- 长文档/视频清洗：精确+模糊去重、视频帧感知哈希、质量过滤、结构校验
- **上采样**长文档，避免被短序列淹没
- **合成**长上下文数据：排列/拼接多模态文档与子任务，使任务必须跨全 1M 上下文注意

**超参**：cosine 学习率衰减（优于 WSD）+ 1% 线性 warmup + weight decay 0.1

### 1.4 后训练数据（§4）

- 三阶段：SFT → RL（3领域×3 effort = 9专家）→ MOPD 蒸馏聚合
- 知识图谱引导的任务合成（§4.2.2）：自演化层级知识图，按概念采样控制领域覆盖度
- QAT 从 SFT 阶段贯穿：MXFP4权重/MXFP8激活

### 1.5 K3 局限

- **未披露具体领域配比百分比**，仅称"各领域采样率由小模型消融实验确定"
- 技术报告 PDF 可从 GitHub 下载：`https://raw.githubusercontent.com/MoonshotAI/Kimi-K3/main/k3_tech_report.pdf`

## 3. DeepSeek V3 技术报告

**来源**：arXiv:2412.19437  
**模型规模**：671B 总参数 MoE，37B 激活参数  
**预训练规模**：14.8T tokens  

### 3.1 数据构造（§4.1）

- 相比 V2：**提升数学和编程样本比例** + **扩展多语言覆盖**（超越英语和中文）
- 数据处理流水线优化：减少冗余同时保持语料多样性
- Document packing 方法（不做 cross-sample attention masking）
- FIM（Fill-in-Middle）策略，rate=0.1，PSM 框架
- Byte-level BPE，128K vocabulary
- **未披露具体领域配比百分比**（仅说"提升数学/编程比例"）

### 3.2 训练超参（§4.2）

- 最大序列长度：4K
- LR schedule：warmup → constant (10T) → cosine decay (4.3T) → constant 低LR (500B annealing)
- Batch size：3072 → 15360 渐进增长
- MTP loss weight：0.3 (前10T) → 0.1 (后4.8T)
- Weight decay: 0.1, gradient clipping: 1.0

### 3.3 V3 局限

- 数据构造章节非常简短（约1页），无具体配比数字
- 仅定性描述数据变化方向

## 4. DeepSeekMath 论文（最相关）

**来源**：arXiv:2402.03300  
**标题**：DeepSeekMath: Pushing the Limits of Mathematical Reasoning in Open Language Models  
**模型规模**：7B（基于 DeepSeek-Coder-Base-v1.5 7B 继续预训练）  
**预训练规模**：500B tokens（其中 120B 数学 tokens 来自 Common Crawl）

### 4.1 迭代数据选择流水线（§2.1）— 核心可借鉴内容

从 Common Crawl 中迭代挖掘数学语料的完整流水线：

**步骤 1：种子语料选择**
- 选择 OpenWebMath 作为初始种子语料
- 随机抽取 500,000 条作为正例
- 从 Common Crawl 中随机抽取 500,000 条作为负例

**步骤 2：训练 fastText 分类器**
- 向量维度：256
- 学习率：0.1
- 最大 word n-gram：3
- 最小词频：3
- 训练轮数：3

**步骤 3：Common Crawl 去重**
- URL-based 去重 + 近似去重
- 91 个 dump 跨批次去重 → 89.8% 去重率（单 dump 仅 22.2%）
- 去重后得到 40B HTML 页面

**步骤 4：召回 + 排序**
- 用 fastText 从去重后的 CC 中召回数学页面
- 按分数排序，仅保留 top-ranking 页面
- 测试不同保留量：top 40B / 80B / 120B / 160B tokens
- 第一轮选择保留 top 40B tokens

**步骤 5：领域扩展（Domain-based Enrichment）**
- 将整个 CC 按基础 URL 组织为不重叠的域
- 计算每个域中被收集页面的百分比
- **域内 >10% 页面被收集 → 标记为"数学相关"域**（如 mathoverflow.net）
- 人工标注该域内的数学 URL（如 mathoverflow.net/questions）
- 将未收集的相关页面加入种子集 → 训练改进的 fastText 模型

**步骤 6：迭代**
- 4 轮迭代 → 35.5M 数学网页 → **120B tokens**
- 第4轮：~98% 数据已在第3轮收集到 → 停止

**步骤 7：去污染（Decontamination）**
- 10-gram 精确字符串匹配过滤基准测试数据
- 对 <10 gram 但 ≥3 gram 的文本使用精确匹配
- 过滤 GSM8K、MATH、CMATH、AGIEval 等基准的题目和答案

### 4.2 数据配比（§2.3）— 明确百分比

DeepSeekMath-Base 7B 的 500B tokens 训练数据分布：

| 数据源 | 比例 |
|---|---|
| DeepSeekMath Corpus（数学） | **56%** |
| Github code | **20%** |
| arXiv | **10%** |
| Natural Language（CC, 中英） | **10%** |
| AlgebraicStack（数学代码） | **4%** |
| **总计** | **500B tokens** |

训练设置：LR max=4.2e-4，batch size=10M tokens，context length=4K

### 4.3 语料质量对比（§2.2, Table 1）

在 DeepSeek-LLM 1.3B 上训练 150B tokens 的对比结果：

| 语料 | 大小 | GSM8K | MATH | MMLU STEM | CMATH |
|---|---|---|---|---|---|
| 无数学训练 | - | 2.9% | 3.0% | 19.5% | 12.3% |
| MathPile | 8.9B | 2.7% | 3.3% | 15.7% | 1.2% |
| OpenWebMath | 13.6B | 11.5% | 8.9% | 29.6% | 16.8% |
| Proof-Pile-2 | 51.9B | 14.3% | 11.2% | 29.2% | 19.9% |
| **DeepSeekMath Corpus** | **120.2B** | **23.8%** | **13.6%** | **33.1%** | **41.5%** |

- DeepSeekMath Corpus 是 Minerva 数学网页的 ~7 倍，OpenWebMath 的 ~9 倍
- Proof-Pile-2 实验中使用 arXiv:Web:Code = 2:4:1 比例

### 4.4 Code vs Math 消融实验（§5.1.1, Tables 6-7）

**实验设置**：DeepSeek-LLM 1.3B，测试不同训练顺序和混合策略

| 训练设置 | Code | Math | GSM8K | MATH | MMLU | BBH | HumanEval |
|---|---|---|---|---|---|---|---|
| 无后续训练 | - | - | 2.9% | 3.0% | 24.5% | 28.1% | 12.2% |
| 通用→数学 两阶段 | 400B(通用) | 150B | 19.1% | 14.4% | 33.1% | 32.7% | 12.8% |
| **Code→数学 两阶段** | **400B** | **150B** | **21.9%** | **15.3%** | **36.2%** | **35.3%** | 12.2% |
| 纯数学 | - | 150B | 20.5% | 13.1% | 32.3% | 32.5% | 11.6% |
| Code+数学 混合 | 400B | 150B | 17.6% | 12.1% | 33.5% | 35.6% | **29.3%** |

**关键结论**：
1. **Code 训练先于 Math 训练效果最好**（GSM8K 21.9% vs 纯数学 20.5%）
2. Code 训练提升 program-aided 数学推理（GSM8K+Python: Code→Math 17.4% vs 纯数学 11.4%）
3. **混合训练缓解遗忘**（HumanEval 保持 29.3% vs 两阶段降到 12.2%）
4. 但混合训练损害纯数学推理（小模型容量限制）
5. Code 训练也提升无工具数学推理和 MMLU/BBH

### 4.5 arXiv 数据无效（§5.1.2）

**反直觉发现**：arXiv 论文对数学推理无改善甚至有害

| 模型 | 语料 | GSM8K | MATH | MMLU STEM | CMATH |
|---|---|---|---|---|---|
| DS-LLM 1.3B | 无数学训练 | 2.9% | 3.0% | 19.5% | 12.3% |
| DS-LLM 1.3B | MathPile (8.9B, >85% arXiv) | 2.7% | 3.3% | 15.7% | 1.2% |
| DS-LLM 1.3B | ArXiv-RedPajama (28B) | 3.3% | 3.4% | 9.0% | 7.4% |
| DS-Coder 7B | 无数学训练 | 29.0% | 12.5% | 38.1% | 45.9% |
| DS-Coder 7B | MathPile | 23.6% | 11.5% | 35.8% | 37.9% |
| DS-Coder 7B | ArXiv-RedPajama | 28.1% | 11.1% | 35.2% | 42.6% |

形式数学（miniF2F）也下降：无训练 20.1%/21.7% → MathPile 16.8%/16.4% → ArXiv-RedPajama 14.8%/11.9%

**可能原因**：arXiv 主要是证明和理论，与实际数学问题求解模式不匹配

### 4.6 SFT 数据构造（§3.1）

- 总计 776K 训练实例
- 英文数学数据：GSM8K/MATH 工具集成解答 + MathInstruct 子集 + Lila-OOD（CoT/PoT）
- 中文数学数据：K-12 76 个子主题，CoT + 工具集成推理格式

## 5. DeepSeek LLM 论文

**来源**：arXiv:2401.02954  
**标题**：DeepSeek LLM: Scaling Open-Source Language Models with Longtermism  
**预训练规模**：2T tokens（中英双语）

### 5.1 预训练数据流水线（§2.1）

三阶段流水线：**去重 → 过滤 → 重新配比（Remixing）**

**去重**：
- 激进跨批次去重策略
- 91 个 dump 跨批次去重 → 89.8% 去重率

| Dumps | 1 | 2 | 6 | 12 | 16 | 22 | 41 | 91 |
|---|---|---|---|---|---|---|---|---|
| 去重率(%) | 22.2 | 46.7 | 55.7 | 69.9 | 75.7 | 76.3 | 81.6 | **89.8** |

**过滤**：语言学 + 语义评估，从个体和全局视角评估文档质量

**Remixing**：调整数据不平衡，增加欠表示领域的比例

**Tokenizer**：BBPE，100K 常规词表 + 15 特殊 token = 100,015，训练语料 24GB 多语言

### 5.2 数据质量影响 Scaling Law（§3.3）— 重要发现

| 数据集 | 质量评估 | 模型指数 a | 数据指数 b |
|---|---|---|---|
| OpenWebText2 | 最高 | 0.578 | 0.422 |
| Current in-house | 中等 | 0.524 | 0.476 |
| Early in-house | 最低 | 0.450 | 0.550 |

**核心洞察**：
- **数据质量越高 → 最优分配越偏向模型扩展（a↑），而非数据扩展（b↓）**
- 可作为间接评估数据质量的方法
- 直觉解释：高质量数据逻辑清晰、预测难度低，更适合扩大模型而非增加数据

### 5.3 SFT 数据配比（§4）

- 总计 **1.5M 实例**
- 有用数据 1.2M：**31.2% 通用语言 + 46.6% 数学 + 22.2% 代码**
- 安全数据 300K

### 5.4 数据消融发现（§5.5）

**选择题数据（MC, 20M）排除**：
- 提升 MC 基准但对生成式任务无益 → 过拟合基准，排除出预训练和微调

**指令数据（5M）在预训练末尾 10%**：
- 效果等价于 SFT 阶段加入 → 最终排除

**数学 SFT 数据增加 → 重复率上升**：
- 7B 模型 stage-1 重复率 2.0% → stage-2（排除数学/代码）降到 1.4%
- 67B 模型 stage-1 重复率 <1% → 不需要 stage-2

### 5.5 DeepSeek LLM 局限

- **未公布预训练领域的具体配比百分比**
- 仅定性描述"比例迭代优化"
- 过滤标准仅定性描述，无数值阈值

### 6.3 对 QuaDMix 的启示

1. **迭代分类器方法**（DeepSeekMath）：可直接借鉴 fastText 迭代选择流水线，用小模型消融定采样率与 QuaDMix 的 proxy 思路一致

2. **数据质量 → Scaling Law 分配**（DeepSeek LLM）：数据质量越高，最优分配越偏向模型扩展——这为 QuaDMix 的 proxy 外推提供了理论支撑

3. **复述优于重复**（Kimi K2/K3）：复述10次×训练1轮 (28.94) > 原始重复10轮 (23.76)，提升 ~22%——数据多样性比单纯增加 epoch 更重要

4. **arXiv 无效**（DeepSeekMath）：反直觉发现，arXiv 论文对数学推理无改善——提醒数据选择不能仅凭直觉，需消融验证

5. **Code→Math 两阶段**（DeepSeekMath）：Code 预训练后再 Math 训练效果最好——训练阶段顺序影响最终性能

6. **跨批次去重**（DeepSeek LLM）：91 dump 去重率 89.8% vs 单 dump 22.2%——去重范围越大效果越好

7. **选择题数据排除**（DeepSeek LLM）：MC 数据提升基准但不提升真实能力——需警惕数据选择中的基准过拟合
